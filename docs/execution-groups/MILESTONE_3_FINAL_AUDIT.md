## SECTION C: POINTS & ATTENDANCE INTEGRITY AUDIT

1. **Zero Client-Side Points Fabrication:**
   - The frontend codebase (`web/src/app/volunteer/*`) contains no point multipliers, attendance hour formulas, or point minting logic.
   - All points, hours, and rankings displayed on the Dashboard, Activity, Leaderboard, and Profile pages are derived exclusively from FastAPI API responses (`/gamification/summary`, `/gamification/ledger`, `/gamification/leaderboard`).
2. **Authoritative Backend Ledger:**
   - Gamification points reside in PostgreSQL table `point_transactions`, protected by database check constraints:
     - `chk_points_sum`: Enforces `total_points = event_points + hour_points`.
     - `chk_point_transactions_type`: Restricts transaction types to canonical values.
3. **Immutable History:**
   - Point transactions are strictly append-only. There are no `UPDATE` or `DELETE` endpoints exposed for volunteer point ledgers.
4. **Duplicate Prevention:**
   - Unique constraints on attendance and event completion prevent double-awarding of points for the same volunteering instance.
5. **Attendance vs. Registration Distinction:**
   - Registration status (`SUBSCRIBED`, `SELECTED`, `WAITLISTED`) does not award points or hours.
   - Points and credited hours are only awarded upon verified coordinator check-in/out in `attendance_records` with status `ATTENDED`.
   - Incomplete sessions (missing checkout) carry status `INCOMPLETE` and award zero completed event points.

## SECTION D: PRIVACY & SECURITY AUDIT

1. **DPDP Compliance & Server-Side Filtering:**
   - When a volunteer sets `leaderboard_visible=False` or `name_visible=False` via `PUT /api/v1/consent/me`, the server returns `is_anonymous: True`.
   - The frontend renders `"Anonymous Volunteer"` and suppresses avatar imagery for anonymous entries.
   - Private personal data (email, mobile number, home address, emergency contacts) is completely absent from leaderboard response DTOs.
2. **Consent Persistence & History:**
   - All 6 affirmative consent dimensions are individually toggleable:
     1. `leaderboard_visible`
     2. `media_usage`
     3. `thank_you_emails`
     4. `linkedin_content`
     5. `contact_available`
     6. `name_visible`
   - Verified that updating a consent increments the record `version` and persists across browser refreshes.
   - Optimistic UI updates include error rollback: if an API call fails, the switch state immediately reverts to its previous value.
3. **Role & Status Enforcement (Zero-Trust):**
   - Backend dependency `require_approved_volunteer` in `server/src/api/deps.py` checks both `UserRole.VOLUNTEER` and `UserStatus.APPROVED`.
   - Volunteers with status `PENDING_APPROVAL`, `REJECTED`, or `SUSPENDED` are blocked with `403 Forbidden` from mutating actions.
   - Status banners in `web/src/components/navigation/volunteer-shell.tsx` clearly notify pending/suspended users.
4. **Object-Level Authorization:**
   - Personal endpoints (`/volunteers/me`, `/consent/me`, `/registrations/me`, `/attendance/me`) query the database strictly by `current_user.id` or `volunteer_profile.id`. A volunteer cannot access or mutate another volunteer's private records.
5. **Browser Security & HttpOnly Cookies:**
   - Browser authentication strictly uses HttpOnly `refresh_token` cookies with `SameSite=Lax`.
   - Zero tokens are stored in `localStorage` or `sessionStorage`.
   - All mutating requests (`POST`, `PUT`, `PATCH`, `DELETE`) require and transmit the `X-CSRF-Token` header.
